Setup guide · mobile and web QA

QA Agent setup with Herdr and Claude Code

How to get a Mac ready for a Claude orchestrator to plan and run tests of a mobile app (Xcode simulators and Android Studio emulators) and its web version (Chrome), on several projects at once. Each test strategy runs in an independent Claude worker in its own Herdr pane, and each worker drives a single device.

2skills: one writes the plan, the other runs it
20test strategies in the catalog
6live workers at most per run, plus the orchestrator
1device per worker: never shared

Versions the skills were checked against: Claude Code 2.1.301, Herdr 0.9.1, Maestro CLI 2.11.0, Claude in Chrome extension 1.0.36, @playwright/mcp@0.0.83. Before copying a command, check the --help of the version you have installed.

Architecture

How it works

You work with a Claude session in a Herdr pane: the orchestrator. It boots the devices, builds an instruction package per suite and opens a new pane per lane. A lane is one device: an iOS simulator, an Android emulator, a browser, or the API. Each pane runs a Claude worker that sees only its package and drives only its device. Each project runs its own orchestrator in its own Herdr workspace, so several projects can be tested at the same time.

Memory

An Android emulator uses about 2–4 GB of RAM, an iOS simulator 1–2 GB, a Claude worker about 0.5 GB and a Maestro JVM 0.5–1 GB. On a 16 GB Mac, plan at most 4 devices in total, with no more than 2 Android emulators. Several projects at once share the same machine: add up their lanes.

Step by step

Step-by-step setup

Wherever a value appears between <…>, replace it with yours. Nothing in the skills installs anything on its own: Maestro, AXe, Playwright MCP and Java show up in the plan as decisions for you to confirm.

  1. Install Claude Code and Herdr

    Install Herdr from its repository, github.com/herdrdev/herdr; it updates later with herdr update. Check the versions:

    claude --version herdr --version herdr status # client and server must be compatible

  2. Connect Herdr with Claude Code

    The integration installs a hook that tells Herdr which state each Claude session is in (idle, working, blocked, done). Without it, the orchestrator cannot tell when a worker finished or got stuck.

    herdr integration install claude herdr integration status # must show: claude: current

  3. Show the context percentage in the status line

    The orchestrator reads its own context usage from the pane (ctx:N%) and hands the run to a fresh orchestrator at 70%. The preflight stops if it cannot read it. If you have no status line yet, add this to ~/.claude/settings.json; if you already have one, add ctx:N% to it.

    { "statusLine": { "type": "command", "command": "jq -r '\"ctx:\\(.context_window.used_percentage // 0 | floor)%\"'" } }

  4. Install the Herdr skills and Superpowers

    # Correct use of the Herdr CLI: panes, agents, states npx skills add herdrdev/herdr --skill herdr -g # Coordination layer: delegation contract, reports, PASS/FAIL/BLOCKED npx skills add aerain/herdr-agent-orchestration -g -s herdr-agent-orchestration -a claude-code

    Superpowers is a plugin, installed inside Claude Code:

    /plugin install superpowers@claude-plugins-official

  5. Install the QA skills

    Clone the repo and link both skills, so every change in the repo reaches Claude without copying. From the root of the clone:

    git clone git@github.com:LeonelMazzanSpace/herdr-qa-plan.git cd herdr-qa-plan ln -s "$PWD/writing-qa-test-plans" ~/.claude/skills/writing-qa-test-plans ln -s "$PWD/executing-qa-test-plans" ~/.claude/skills/executing-qa-test-plans ls -l ~/.claude/skills | grep qa-test-plans # both links must show

    To use them in one project only, create the same links inside <project>/.claude/skills/. Open a new Claude Code session and type /: /writing-qa-test-plans and /executing-qa-test-plans must appear. They are manual only (disable-model-invocation: true), so they never start on their own. Update them later with git pull in the clone.

  6. Prepare Android (if you test Android)

    Install Android Studio, create at least one virtual device in Device Manager, and add the SDK tools to your PATH (for example in ~/.zshrc). Android lanes are driven with plain adb: no Maestro and no Java needed. From 16 GB of RAM the plan uses two Android lanes by default (a second AVD, or the same one booted --read-only).

    export ANDROID_HOME="$HOME/Library/Android/sdk" export PATH="$ANDROID_HOME/emulator:$ANDROID_HOME/platform-tools:$PATH" emulator -list-avds # e.g. Pixel_8_API_34 adb version

    The app needs an .apk. With Expo: an EAS profile with "android": { "buildType": "apk" }, or npx expo run:android --variant release.

  7. Prepare iOS (if you test iOS)

    Install Xcode from the App Store and its command line tools. In Xcode, open Settings → Components and download an iOS runtime. Then check there are simulators:

    xcode-select --install xcrun simctl list devices available # note the UDID of the iPhone you will use

    Physical iPhones are not supported: iOS tests run on simulators, so the app needs a simulator build (.app), not an .ipa. With Expo: an EAS profile with "ios": { "simulator": true }, or npx expo run:ios --configuration Release.

    iOS needs one of two drivers. Install it yourself, or let the skill ask you; it never installs on its own:

    # Option A: Maestro CLI, pinned, without piping the script (read it before running it) java -version # 17 or later curl -fsSL "https://get.maestro.mobile.dev" -o /tmp/maestro-install.sh MAESTRO_VERSION=2.11.0 bash /tmp/maestro-install.sh maestro --version # 2.11.0 # Option B: AXe, a single binary, no Java (also the way to run a second iOS lane) brew install cameroncooke/axe/axe axe list-simulators
    Maestro MCP limit

    The Maestro MCP uses fixed ports per platform, so at most one Maestro MCP worker drives an iPhone at a time. A second iOS lane runs on AXe, or runs existing flow files with maestro test. The orchestrator boots the devices with boot-device.sh; the MCP cannot.

  8. Prepare the web (if you test web)

    The default web driver is Claude Code's native Chrome. Install the Claude in Chrome extension from the Chrome Web Store, sign in to the same claude.ai organisation as your claude (/login, a direct Anthropic plan), keep Chrome open, and allow the domains you will test in the extension's site settings. Check with claude --chrome and /chrome in a session of your own.

    Careful

    This lane acts inside your real Chrome, with your logged-in sessions, and you see every tab it opens. Use it only on your own staging or dev sites, ideally from a dedicated Chrome profile with nothing else signed in and the extension allowing only the QA domains. Chrome runs one web lane at a time and cannot emulate a mobile viewport.

    Playwright MCP is opt-in. The plan offers it only for what Chrome cannot do: parallel web lanes, the 375×667 mobile-web pass, headless runs or an isolated profile. It is always the pinned version, never @latest. A Playwright MCP already registered in your own Claude does not count: workers only get the run's config.

    npx -y @playwright/mcp@0.0.83 --help # --isolated, --viewport-size and --output-dir must appear

    If the project has its own Playwright tests (playwright.config.* or @playwright/test in package.json), the plan runs them as a regression suite with the project's runner (pnpm exec, yarn, npm exec --no --; never a bare npx). Their browsers must already be downloaded.

  9. Optional sources: vault and ClickUp

    Both are optional. Without them, the plan records none and carries on.

    • Obsidian vault: install the local REST API plugin with its MCP endpoint in Obsidian and register it. The key is a secret: never put it in a repo file.
    claude mcp add --transport http obsidian-mcp http://127.0.0.1:27123/mcp/ \ --header "Authorization: Bearer <PLUGIN_API_KEY>"
    • ClickUp: connect it from your Claude account's connectors and confirm with claude mcp list. It can be a source (tickets, regression test cases) and a destination (confirmed bugs). If you name no ClickUp, the skill asks once; with no answer, the run never touches ClickUp and delivers the HTML page only.

  10. Prepare the QA project folder

    The skills run from the root of a QA project (for example qa-team-spacedev). They use, when present:

    • .env, copied from .env.example: accounts per role (TEST_USER_EMAIL, ADMIN_EMAIL…) and API keys. Never committed; workers never print its values;
    • context/navigation-map.md and your regression sources: context/regression-flows*.md, context/*uat*.md, context/*test-cases*.md. The planner finds them on its own and audits them before writing the plan;
    • maestro/flows/ with YAML flows, and the project's Playwright suite, if they exist;
    • the builds: simulator .app and .apk.

    The orchestrator creates qa-plans/, evidence/ and QA-SCRATCHPAD.md.

  11. Allow the workers to run commands

    Workers run adb, simctl and Maestro without asking for each command. The recommended mode is --permission-mode auto; the permission classifier may block launching agents that way, so approve it when the orchestrator asks, or add a rule for herdr agent start in settings.json (the update-config skill helps write it). To supervise every step, use acceptEdits and approve commands in each pane. Every worker also starts with deny rules that block reading .env* and dumping the environment. The orchestrator never answers a worker's permission prompt.

One or several platforms

What happens by scope

When writing the plan, the skill asks which platforms are in scope and whether it covers one feature or the whole app. It only plans, checks and boots what belongs to that scope; strategies of the platforms left out are marked not applicable, with the reason.

web only

Browser and, if you want, API

  • One Chrome lane; a second one only with Playwright MCP.
  • Asks the viewport: desktop 1440×900, mobile web 375×667, or both.
  • No Xcode, Android, Java or Maestro.
  • Not applicable: interruptions, install/upgrade, device-only checks.
mobile only

iOS, Android or both

  • One lane per device: adb on Android, Maestro or AXe on iOS.
  • Checks only the tools of the platforms chosen.
  • Never starts a browser.
  • Not applicable: responsive web, and E2E with the web admin unless it is in scope.
mobile + web

Everything

  • iOS, Android and web lanes (and API if asked).
  • Adds cross-platform parity and cross-system E2E: what the app creates is verified in the admin.
  • Up to 5 test lanes at once, plus a verifier.
First use

Plan and run

Open Herdr and start Claude Code inside a pane, so it inherits HERDR_ENV=1. That Claude is the orchestrator. For several projects at once, open one Herdr workspace per project and start an orchestrator in each.

herdr # opens or resumes the Herdr session cd <qa-project> claude # inside the pane > /writing-qa-test-plans > /executing-qa-test-plans qa-plans/2026-11-05-portfolio.md > /executing-qa-test-plans status # progress of a run in progress

/writing-qa-test-plans with nothing else asks, in this order:

  1. the conversation language, alone;
  2. in one message: platforms, area (one feature or the whole app), user types with their .env variable names, and the existing regression with the tickets of the change;
  3. session details: environment and base URL, web viewport, builds, project language.

With an existing regression, it audits it first: each flow ends up valid, changed, deprecated or unclear, and it lists the missing regression (from the tickets, and proposed by the skill, marked proposed ·). The plan comes with a plain-language summary and a list of decisions to confirm: installs, extra devices, the ClickUp destination, the permission mode, and any payment, asked separately per suite. Nothing runs until you confirm. During a run you can ask for "status", "what's left" or "stop everything", and watch or step into any pane.

For the first run

Start small: a smoke on a single lane. It confirms the driver, the permission mode and the context reading on your machine before you open several lanes or several projects.

Output

Where results go

evidence/<app>/ ├── S-001-smoke-ios/<run-id>/ │ ├── qa-report.md # suite report (ClickUp-compatible format) │ └── 01-*.png # numbered screenshots ├── S-005-smoke-web/<run-id>/… ├── QA-RUN-SUMMARY-<run-id>.md # score, prioritised bugs, go / no-go └── QA-RUN-RESULTS-<run-id>.html # results page (always when there is no ClickUp)
  • With ClickUp connected and approved: only bugs confirmed by an independent verifier are filed, after a duplicate search.
  • Without ClickUp: the run never touches ClickUp, even if connected, and delivers the HTML page only. It opens offline; to share it, send the whole evidence/<app>/ folder zipped, since screenshots are linked.
  • Regression set: at closing, the orchestrator offers the audit's proposed updates (retire, rewrite, add, last successful run) with each flow's outcome, and applies only the ones you approve.
  • Internal packages and worker reports: ~/.cache/qa-runs/<run-id>/ (mode 0700).
